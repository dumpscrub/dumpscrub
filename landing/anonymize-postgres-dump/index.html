Anonymize a Postgres dump for staging

You want production-shaped data in staging — same schema, same volumes — without real emails, phones, SSNs, or addresses sitting in a disposable database. DumpScrub works on the dump file, so there's no live database connection and nothing to configure. 

# install and scrub a plain-format dump
$ pipx install dumpscrub
$ pg_dump prod | dumpscrub > staging.sql
$ psql staging < staging.sql

Works with both pg_dump formats

Default plain-format pg_dump emits COPY ... FROM stdin blocks. DumpScrub reads those directly, streaming row by row (flat memory), preserving \N NULLs. If you use --inserts, that works too. 

# native COPY format (the default)
pg_dump prod | dumpscrub > staging.sql

# if you prefer INSERTs
pg_dump --inserts --column-inserts prod | dumpscrub > staging.sql

What gets masked

Columns are detected by name: email, phone, ssn, first_name, last_name, address, city, zip, dob, username, password/token. Replacements are deterministic — the same input always produces the same output, so results are reproducible and join keys stay consistent.

Fix over/under-masking without code

# free-text and odd column names: override per rule
dumpscrub --ignore users.phone \
          --mask orders.ship_address=street_address \
          < prod.sql > staging.sql

# or commit a team-wide policy
cat > .dumpscrub.json <<'JSON'
{ "mask": { "orders.ship_address": "street_address" },
  "ignore": ["audit_log.message"] }
JSON

Gate it in CI

Fail the pipeline if a dump still contains PII, and produce an audit-evidence report (input/output SHA-256) for reviewers. 

dumpscrub prod.sql -o staging.sql --report scrub-report.json
dumpscrub --dry-run --fail-on-pii < prod.sql   # exit 1 if PII remains
